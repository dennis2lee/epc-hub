# 결정 기록

결정마다 날짜, 내용, 이유, 근거(누가·무엇으로 정했는지)를 남긴다. 사용자가 직접 답할 수 없는 항목은 개발 담당이 Fable 자문을 받아 정하고 "잠정"으로 표시한다. 잠정 결정은 당회·재정부 확인 후 바꿀 수 있다.

## 업무 규칙 (2026-11-21, 사용자 확정)

| # | 결정 |
|---|---|
| A1 | 결재는 지출 부서의 부장과 담당 장로만 한다. 재정부는 서명하지 않는다 |
| A2 | 금액에 따른 추가 결재는 없다 |
| A3 | 보완 요청 후 다시 제출하면 부장부터 다시 받는다 |
| A4 | 모든 부서에 담당 장로가 있다. 비어 있으면 제출을 막는다 |
| A5 | 관리자는 사무간사와 개발 담당. 처음에는 이평우 1명. 감사는 감사위원 |

## 구현 결정 (잠정, 2026-11-21, Fable 자문 반영)

사용자가 질문에 답할 수 없다고 해서, 개발 담당이 Fable 자문을 받아 아래와 같이 정했다. 자문 원문 요약은 `doc/reviews/2026-11-21-구현-착수-자문.md`에 있다.

| # | 결정 | 이유 |
|---|---|---|
| D1 | 루트에 설정 파일, `src/app`·`src/lib`(Next.js), `src/supabase`(마이그레이션·pgTAP·시드), `doc/`, `build/`(Next `distDir`=`build/next`, 테스트 산출물). Supabase CLI는 npm 스크립트로만 부른다(`--workdir src`) | 사용자 요구(src·doc·build). 플래그를 빼먹으면 루트에 `supabase/`가 새로 생기는 사고를 막는다 |
| D2 | Next.js 16의 `cacheComponents`와 `partialPrefetching`을 켠 채로 간다. DB 데이터에는 `"use cache"`를 쓰지 않는다 | 다음 메이저에서 기본값이 된다. 사용자별 데이터에 공용 캐시를 쓰면 데이터가 섞일 수 있다 |
| D3 | DB 검증은 Docker(Colima) 위의 `supabase start` + pgTAP. 동시 승인은 Vitest에서 DB 연결 두 개로 따로 시험한다 | 통제가 RLS·권한·잠금에 있어 실제 Postgres와 Supabase 역할이 필요하다 |
| D4 | 알림은 DB 전이 함수가 같은 트랜잭션에서 `notifications` 행을 쓰고, 서버가 service role로 주소를 붙여 보낸다. service role은 `src/lib/server/` 한 곳에서만 쓴다 | "다음 사람이 누구인가"를 DB만 안다. 메일이 실패해도 결재는 진행되고 재시도된다 |
| D5 | 카카오 로그인은 1안(Supabase 카카오 공급자, 이메일 없이)과 2안(카카오 OIDC id_token + `signInWithIdToken`)을 시험판에 함께 넣는다 | 1안이 기본 scope 문제로 실패할 가능성이 있다 |
| D6 | 사람과 로그인 계정은 1:N(`person_logins`) | 카카오 계정과 이메일 계정은 서로 다른 로그인이 된다. 한 사람에게 묶여야 한다 |
| D7 | 날짜 판정은 DB의 `private.local_date()`와 `app_settings.time_zone`(기본 `America/Los_Angeles`, 교회 확인 필요) 한 곳에서 한다 | 서버(UTC)와 교회 날짜가 다르면 12월 31일 저녁 제출이 새해로 넘어간다 |
| D8 | 마이그레이션은 버전 파일로 관리한다. 운영 첫 배포 전에는 파일을 고쳐 쓰고 `db reset`으로 검증하며, 그 뒤로는 추가만 한다 | 선언형 diff는 권한·정책 변경을 놓칠 수 있다 |
| D9 | i18n은 URL에 언어를 넣지 않고 ko/en 사전과 `people.lang`으로 한다. DB 오류 코드(`not_your_turn` 등)를 사전 키로 쓴다 | 한 카톡 링크를 한·영 사용자가 같이 쓴다 |
| D10 | 저장소는 GitHub private `dennis2lee/intra-net`, 브랜치는 `main`과 마일스톤 브랜치 | 1인 개발 |
| D11 | 영수증 업로드는 서버 액션을 거친다. 서버가 파일 형식을 바이트로 확인하고 sha256을 계산한 뒤, 작성자·작성 중 상태를 확인하고 service role로 Storage에 올린다(파일당 4MB 이하, 휴대폰에서 축소, 청구당 20장). 사용자는 버킷에 직접 쓸 수 없고, 파일은 첨부 행을 통해서만 읽는다(감사위원은 뺀 파일도 읽음). 화면은 요청마다 60초짜리 서명 URL을 새로 만드는 경로로 영수증을 연다. (M2 레드팀으로 개정) | 해시와 형식을 클라이언트가 주장하지 않게 한다. 직접 업로드로 검사를 우회한 파일이 쌓이지 않게 한다. 결재자가 오래 열어 둔 화면에서도 영수증이 열린다 |
| D12 | 결재 관계자(부장·장로·재정부·관리자)는 초대 링크로 연결해도 "사무실 확인 중"으로 두고 대면 확인 후 활성화한다. 일반 작성자는 휴대폰 뒤 4자리가 맞으면 바로 활성화한다 | 설계서 8장 |
| D13 | 재정 처리(서류 확인·수표 기록)는 작성자와 그 회차 결재자가 할 수 없다. 처리할 재정부원이 없으면 재정 담당 장로가 하고, 그래도 없으면 막힌 건 목록에 오른다 | 한 사람이 승인과 지급을 함께 하지 못하게 한다(M1 레드팀). A9를 넓힌 해석이라 당회 확인 필요 |
| D14 | 한 번이라도 제출된 청구의 영수증 파일은 지우지 않는다. 작성자가 첨부를 빼도 파일은 증거로 남는다 | 결재자가 본 내용의 증거 보존(M1 레드팀) |
| D15 | 관리자가 2명 미만인 기간에 제출된 청구는 `solo_admin_period`로 표시해 감사 보고에 모은다. 관리자는 자신을 대면 확인할 수 없다 | 초기 1인 운영의 견제(설계서 6장) |
| D16 | 수표 수취인은 제출 시점의 영문 이름으로 고정하고 승인 해시에 넣는다. 영문 이름이 없으면 제출할 수 없다 | 승인 후 수취인 변경 차단(M1 레드팀) |

## M2·M3 레드팀 후속 결정 (잠정, 2026-11-21, Fable 자문 반영)

M2·M3 레드팀 결과(`doc/reviews/2026-11-21-m2-redteam.md`, `doc/reviews/2026-11-21-m3-redteam.md`)를 받아 Fable 재정 통제 자문을 거쳐 정했다. "당회 확인"이 붙은 항목은 시범 운영 전에 당회 확인을 받는다.

| # | 결정 | 이유 |
|---|---|---|
| D17 | HEIC 사진은 서버가 받지 않는다. 휴대폰 브라우저가 해독할 수 있으면(사파리) 올리기 전에 JPEG로 바꾼다. 안 되면 "카메라 설정에서 높은 호환성"을 안내한다 | 안드로이드·크롬 결재자 화면에서 HEIC가 깨져 보이는데도 "영수증 N장 승인"이 눌린다 |
| D18 | 화면 언어 선택은 영어 화면이 완성될 때까지 숨긴다. 그동안 모든 화면은 한국어 본문 + 영어 보조 문구이고, 오류 문구는 두 줄(한국어, 영어)로 낸다. `people.lang`은 그대로 저장한다 | 저장만 되고 반영되지 않는 설정은 2세대 사용자를 혼란스럽게 한다 |
| D19 | 월별 CSV는 수표 발행월(현금 기준) 하나로 낸다. 그 달에 발행한 모든 수표가 나오고, 무효 수표는 금액 0으로 함께 나온다(번호 연속 확인). 미지급 청구와 미결제 수표는 "오늘 기준" CSV로 따로 낸다. 취소 청구는 넣지 않는다. 월 마감 잠금은 다음 버전으로 미루고, 지난달 발행일로 기록한 건은 `소급 기록`으로 표시한다. 내려받기는 감사 로그에 남긴다 | 발행월과 사용일을 섞으면 한 건이 두 달에 나오거나 빠진다. 마감 잠금은 마감 주체·해제 절차를 당회가 정해야 한다 |
| D20 | 수표 무효: 묶인 모든 청구의 재정 처리자(D13)가 할 수 있고 발행자 본인도 된다. 사유 5자 이상 필수, 수표 한 장 전체만, `issued` 상태만. 무효 후 청구는 `received`로 돌아가고 작성자에게 알린다. 무효 번호는 다시 쓰지 않는다. 재발행 수표는 무효 수표를 가리키고, 무효 처리일보다 앞선 날짜로 발행할 수 없다. 발행자 본인 무효는 **당회 확인** | 무효는 돈이 나가는 것을 막는 방향이라 위험이 낮다. 2~4명 재정부에서 본인 금지는 업무를 멈춘다. 기록과 감사 노출로 통제한다 |
| D21 | 은행 결제 기록: 수취인과 그 회차 결재자는 못 한다. 발행자는 다른 자격자(재정부원·재정 담당 장로)가 한 명이라도 있으면 못 하고, 없을 때만 하며 `발행자 본인 결제 기록`으로 표시한다. 감사위원은 보기만 한다. 잘못 기록하면 사유를 적고 취소할 수 있다. 발행·무효·결제·취소는 지울 수 없는 `payment_events`에 쌓인다. 대체자가 없을 때 발행자 본인 기록 허용은 **당회 확인** | 수표를 쓴 사람이 은행 대사까지 하면 위조·변조를 숨길 수 있다. 감사위원이 기록하면 감사 독립성이 깨진다 |
| D22 | 재정부는 서류 확인(`received`) 뒤에도 서류 보완 요청을 보낼 수 있다. 살아 있는 수표가 있으면(`paid`) 못 한다. 반송하면 서류 확인 기록이 지워지고, 다시 결재를 거친 뒤 새로 확인한다 | 수표를 쓰려다 서류 문제를 발견하는 일이 실제로 있다. 막으면 틀린 서류로 지급하게 된다 |
| D23 | 수표를 기록할 때 수표에 실제 쓴 금액을 한 번 더 넣고, 고른 청구 합계와 다르면 거부한다(묶음·단건 모두) | 묶음에서 한 건이 빠지거나 더해지는 실수를 가장 싸게 잡는다 |
| D24 | 수표 번호는 숫자 1~10자리만 받는다. 전각 숫자는 바꾸고 앞의 0은 뗀다. `#`, 공백, 글자가 섞이면 거부한다 | 유사 번호(`1024`와 `1024A`, `#1024`)로 중복 검사를 피하지 못하게 한다 |
| D25 | 알림 메일은 응답을 보낸 뒤(`after`) 보내고, 행을 잡을 때 `claimed_at`을 남겨 10분 넘게 멈춘 행만 되찾는다(재시도 횟수 증가, 3회면 실패). 다음 결재자에게 메일 주소가 없거나 발송이 실패하면 막힌 건 목록에 바로 오르고, 화면이 "카톡이나 전화로 알려 주세요"라고 말한다. 알림 메일 주소를 바꾸면 이전 주소로 안내 메일이 간다 | 느린 메일 서버가 승인 버튼을 붙잡지 않게 하고, 같은 메일을 두 번 보내지 않으며, 알림이 조용히 사라지지 않게 한다 |
| D26 | 매일 점검 메일은 하루 한 번만 보낸다(`digest_runs`). 관리자에게 막힌 건, 재정부에게 90일 넘은 미결제 수표와 재정 처리자 없는 건을 보낸다. 막힌 건이 없으면 월요일에 "이상 없음"을 보낸다 | Cron이 겹쳐도 중복 발송하지 않고, Cron이 멈춘 것을 알아챌 수 있게 한다 |
