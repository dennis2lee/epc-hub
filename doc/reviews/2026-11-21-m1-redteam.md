# M0·M1 레드팀 검토 (Fable, 2026-11-21)

M0(기반·로그인 시험판)과 M1(DB 핵심)이 끝난 뒤 Fable 모델 세 명이 따로 검토했다. 모두 읽기 전용으로 검토했고, DB 실험은 `BEGIN … ROLLBACK` 안에서만 했다. 아래는 지적 요지와 조치다. 회귀 테스트는 `src/supabase/tests/02_redteam_regressions_test.sql`에 있다.

## 1. 로그인·서버 코드 (12건)

| 심각도 | 지적 | 조치 |
|---|---|---|
| 높음 | `next` 파라미터에 탭 문자를 넣으면 오픈 리다이렉트 (`/\t/evil.com`) | 제어 문자·역슬래시 거부, URL로 다시 해석해 같은 출처만 허용. 테스트 추가 |
| 높음 | 카카오 방식 2가 nonce 원문을 양쪽에 보내 Supabase 검증이 실패할 것 | 카카오에는 sha256 해시, Supabase에는 원문. id_token 검증은 Supabase 카카오 공급자가 하므로 운영에서도 켜 두어야 함을 문서화 |
| 중간 | 이메일 확인 꺼짐, OTP 1시간 | 확인 켬, OTP 10분 |
| 중간 | 업로드 한도 불일치(5MB·10MB·4MB), 형식을 브라우저 주장대로 저장 | 4MB로 통일, 서버가 파일 첫 바이트로 형식 판정(`file-type.ts`) |
| 중간 | 오류 문구를 로그인 화면에 그대로 반사 | 짧은 코드만 전달하고 고정 문구로 변환 |
| 중간 | 카카오 토큰 교환에 타임아웃·예외 처리 없음 | 8초 타임아웃, 실패 시 코드로 안내 |
| 중간 | 메일 앱에 다녀오면 코드 입력 단계가 사라짐 | sessionStorage에 진행 상태 보관 |
| 낮음 | redirect_uri를 요청 Host로 구성 | `NEXT_PUBLIC_SITE_URL` 고정 주소 사용 |
| 낮음 | 로그아웃 Origin 검사 없음, 전 기기 로그아웃 | Origin 검사, 이 기기만 로그아웃 |
| 낮음 | 보안 헤더 없음(결재 버튼 클릭재킹) | `frame-ancestors 'none'` 등 추가 |
| 낮음 | 운영에서 메일 키가 비면 메일 내용이 로그에 남음 | 운영에서 필수로 |
| 낮음 | CI에 빌드 단계 없음 | 빌드·typegen·통합 테스트 추가 |

## 2. 업무 규칙 (15건 중 주요)

| 심각도 | 지적 | 조치 |
|---|---|---|
| 높음 | 부장과 담당 장로가 같은 사람이면 그 부서는 제출 불가(`return query` 뒤 계속 실행되는 버그) | 수정, 1단계·두 역할로 결재. 테스트 추가 |
| 높음 | 한 사람이 승인·서류 확인·지급을 모두 할 수 있음 | 그 회차 결재자는 재정 처리 불가(D13). 처리할 사람이 없으면 막힌 건 목록 |
| 높음 | 승인 후 작성자가 수표 수취인 이름을 바꿀 수 있음 | 제출 때 영문 이름 필수, 청구서에 고정, 승인 해시에 포함 |
| 중간 | 중복 영수증 탐지가 약함, 재정부 확인 사유 없음 | 같은 청구 안 같은 파일 금지, 겹치는 청구를 표로 기록, 중복 의심 건은 확인 사유 필수 |
| 중간 | 이미 활성인 교인에게 직책을 주면 대면 확인 없이 결재 | 직책 보유자는 대면 확인(`in_person_checked_at`) 후에만 결재·재정 처리 |
| 중간 | 빠져나올 길 없는 막힘 | 관리자의 현재 단계 재지정, 작성자의 청구 취소, 제출 차단·처리자 없음을 막힌 건 목록에 표시 |
| 중간 | 수표 번호·발행일 검증 약함 | 번호 정규화, 중복 코드, 미래 날짜·서류 확인 전 날짜 거부, 무효 수표 번호 재사용 허용 |
| 중간 | 다시 제출하면 60일 판정과 첫 제출 시각이 덮어써짐 | `first_submitted_at` 기준으로 판정, 재정부 반송을 회차별로 기록 |
| 중간 | 회수 후 알림이 그대로 발송, 번호 받은 청구 삭제 가능 | 회수 시 알림 취소, 번호 있으면 삭제 대신 취소 |
| 중간 | 서류 확인 시 "수표 준비됨" 알림, 수표 한 장에 N통 | `documents_verified`로 바꾸고 수표당 1통 |
| 낮음 | 대기 상태에서 임시저장 불가, 비활성 부서 제출, 해외 영수증 날짜 | 대기 상태 임시저장 허용, 제출 때 부서 재검사, 미래 날짜 하루 여유 |

## 3. DB 보안 (15건 중 주요)

| 심각도 | 지적 | 조치 |
|---|---|---|
| 높음 | 관리자 1인이 가짜 인물로 청구부터 지급까지 혼자 완료 | 관리자는 자신을 대면 확인할 수 없음, 재정 직책은 재정부에만, 직책 보유자는 대면 확인 전 결재 불가, 관리자 1인 기간의 청구에 표시(`solo_admin_period`). 근본 해결은 두 번째 관리자 등록(C4) |
| 높음 | `add_attachment`가 해시·형식을 호출자 주장대로 믿음 | 클라이언트 실행 권한 회수, 서버 전용 `add_attachment_srv`가 Storage 메타데이터로 형식·크기·소유자 확인 |
| 높음 | 영수증 파일 삭제 정책이 있어 제출 후 증거 파기 가능 | 삭제 정책 제거. 한 번도 제출되지 않은 청구의 파일만 서버가 지움. 제출 때 파일 실물 존재 확인 |
| 중간 | 초대 뒤 4자리 무차별 대입 | 5회 실패 시 잠금, 새 초대가 이전 초대를 무효화 |
| 중간 | `p_version`에 NULL을 넣으면 버전 검사 우회 | 모든 함수를 `is distinct from`으로 |
| 중간 | 첨부 추가·삭제가 청구 행을 잠그지 않음 | 행 잠금 추가 |
| 중간 | 감사 기록을 service role이 지울 수 있음, 행위자 NULL | 모든 역할에서 수정·삭제·TRUNCATE 금지 트리거, DB 역할 기록, 서버 호출의 행위자 전달, 영수증 파일 변경도 기록 |
| 중간 | 읽기 범위가 설계보다 넓음 | 결재자는 자기 차례부터 또는 결정한 뒤만, 작성 중인 청구는 작성자만 |
| 낮음 | 기본 권한이 남아 다음 마이그레이션의 객체가 열린 채 생김 | default privileges 회수, 정책 없는 표의 SELECT 회수 |

## 4. 남은 것 (다음 마일스톤에서)

- 동시 제출·승인·지급 시험(연결 두 개, Vitest) — M2 레드팀 전에 추가
- 시험판 버킷(`trial`)은 교인이 아닌 로그인도 쓸 수 있다. 크기·형식을 제한했고, 실기기 시험이 끝나면 버킷과 정책을 지운다
- 소속 부서 개념(아무 부서로나 청구 가능)은 교회 결정이 필요하다(A10과 함께)
- D13(재정 담당 장로가 처리하는 범위)은 잠정이다. 당회 확인 필요
